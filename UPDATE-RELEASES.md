# Publishing automatic updates

Automatic updates apply to the installed Windows app from v0.8.0 onward. Older installed copies need one manual installation of v0.8.0 or later. Portable/source downloads do not update themselves.

## What users receive

The installed app checks shortly after startup and every six hours. It accepts newer stable versions only. It downloads an authenticated update in the background and installs on normal app quit, after the owned local server stops. A visible notice offers **Restart now**, which defers while any generation or terminal process is running. Closing with open terminal agents asks whether to stop them first. No forced restart is scheduled. Users can opt out in **Help → Automatic updates**.

An offline, incomplete or untrusted release produces a recoverable update notice and leaves the app usable. An installer is never downloaded before the detached Ed25519 manifest signature, version, filename, size and SHA-512 match the app's pinned release identity and updater metadata. The standard updater additionally verifies the downloaded file checksum. No update credentials are shipped in the app.

## Release procedure

1. Bump the root, desktop and terminal-host package versions and their lockfiles together. Keep the stable `major.minor.patch` format and the existing application ID/data paths.
2. Commit and push the reviewed code to main. Create a **draft** GitHub release tagged `v<version>` and target that exact commit SHA.
3. Dispatch **Build portable releases** and **Windows desktop installer** on main, passing the draft release ID and exact commit SHA.
4. The Windows workflow compiles/tests/packages, verifies real installation and a two-version automatic-update fixture, then signs the tested installer metadata using the repository secret `VIZOR_UPDATE_SIGNING_KEY`. Only after those checks does it upload the release files.
5. Require all jobs to pass and confirm the release has its complete assets before publishing. Drafts and prereleases are not delivered automatically. Merely pushing source changes does not update users.

Windows automatic-update assets must travel together in the same release:

- `Vizor-Setup-<version>-x64.exe` and its `.sha256` file.
- `Vizor-Setup-<version>-x64.exe.blockmap` for differential downloads/fallback.
- `latest.yml`, generated by electron-builder for that exact installer.
- `vizor-update.json` and `vizor-update.sig`, generated by `npm run release:sign-update` after verification.

The existing portable assets and combined SHA256SUMS.txt remain useful for manual downloads. Do not edit an installer or its YAML after signing; rebuild and verify it instead. Do not publish a release with missing updater files.

## Release key custody

`desktop/update-key.cjs` contains only the public verification key. The permanent private Ed25519 key is configured as the GitHub Actions repository secret `VIZOR_UPDATE_SIGNING_KEY`, encoded as base64 PKCS#8 DER. A private local backup is in the ignored `.release-secrets/` directory. Back it up securely; never commit or share it or include it in a downloadable package. The workflow makes the secret available only to the post-test signing step. It is not present during compilation or in the app.

This key authenticates updates; it is **not** a Windows publisher certificate and does not remove SmartScreen/unknown-publisher warnings. No Microsoft Store account, paid signing service or changes to Windows security settings are involved.

Never silently regenerate the key. Existing apps pin the old public identity and will reject a replacement signer. Rotate by shipping a transition release trusted by the old key before removing it. If a release is withdrawn, publish a newer corrected version; automatic downgrades are blocked. Preserve both `.env` and the database when manually rolling back code/data together.

## Verification boundaries

`npm run test:updates` builds two **private test applications**, with a different application ID, temporary workspace, localhost feed and ephemeral signing key. It verifies actual updater download, busy-restart deferral, installation on normal quit, a newer app relaunch and retained data. These fixture packages are never uploaded as Vizor releases. Production packages are checked against their production updater source/public key and fixed GitHub feed. Normal installed-app checks disable network updates; provider operations in separate tests use mocks.
