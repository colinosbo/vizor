# Vizor product and engineering handoff

Prepared November 17, 2026. Audience is the Vizor maintainer or implementation agent taking over productization after the Vision pilot.

## Outcome and owner decisions

A user connects a repository and workers, agrees to a plan, and can follow delivery through a single dashboard. Vizor creates an ordered backlog, starts eligible work, observes results, merges code when configured checks pass, and advances dependencies. Routine project progress should continue through usage pauses and machine restarts without the owner returning to this chat to release tasks.

The owner requested the following behavior during this pilot.

- Use one worker chat per assignment. A usage-limited session stays with that assignment and resumes when its provider allowance resets. Reassign only after confirming the original run ended or the owner explicitly requests a transfer.
- Use GitHub Actions and deterministic tests for code merge decisions. The owner removed the Codex timer and AI review requirement. A passed test suite can still miss bugs, so display the actual checks and their results.
- Automatically accept completed research and verification tasks for the POC. Keep exceptions visible when actual customer permission, spending, or external commitments are required.
- Use short-lived branches and PRs for coherent implementation changes. An approved plan can span many branches. Keep the official default branch usable.
- Show each agent's current assignment, specific blocker and next assignment on one screen. Read existing project configuration and queue state without a second manual connection process.
- Phase 2 startup is authorized after Phase 1's final result. Customer workspace access and spending still require an actual named target and agreed limits.

## Universal setup and data contract

Use the current scheduler and receipt model as the starting point. Introduce a versioned initiative manifest owned by the project manager and approved by the owner. It should capture the following records without embedding secrets.

| Record | Required information |
|---|---|
| Initiative | Stable ID, repository identity and host, resolved local folder, default branch, approved plan revision and current phase |
| Worker | Stable ID, display name, provider adapter, permitted role, capability flags and credential reference |
| Task | Stable draft ID and GitHub issue, owner, dependencies, outcome, allowed paths, acceptance evidence, branch/PR/artifact and gate policy |
| Runtime | Selected transport, installed version, OS identity, state location, health and startup policy |
| Merge policy | Required check identities, approved task/plan scope, path rules, hold labels and post-merge verification |
| Attempt | Assignment ID, worker and provider run, request time, delivery outcome, error category and immutable recovery history |
| Queue decision | Current task status, dependency reasons, eligible next task, current pause/approval exception and observation time |

Migration must preserve existing issue numbers, accepted artifacts, receipt deduplication and provider sessions. Import the current queue JSON and repository-keyed SQLite database before enabling a new loop. Detect a live scheduler and attach to it. Use one dispatch authority per initiative, including across desktop and CLI launches.

A fresh setup should finish with the user's repository and workers already visible on the dashboard. Existing projects should show their live assignments during import. Starting another orchestrator or creating another provider chat must be an explicit work action.

## Acceptance scenarios before claiming a universal autonomous release

1. A new user installs Vizor, connects a private GitHub repo and two or more differently named workers, approves a plan and sees the populated dashboard. No source edits or developer filesystem paths are required.
2. One research artifact and two code tasks complete in dependency order. Independent assignments overlap safely. A failed check holds the dependent task, a corrected push resumes it, and GitHub verifies the exact merged revision before release.
3. Reboot during an active run. After the documented startup condition, the same task/run is restored, GitHub results reconcile and no duplicate session appears. Show the pre-login limitation if startup requires sign-in.
4. Pause a provider routine and exhaust usage in another run. Display distinct reasons. Re-enable/resume using the existing assignment, and verify the next task starts automatically after completion.
5. Drop the fire response after provider acceptance and separately return a confirmed rejection. Reconcile the ambiguous attempt without duplicate execution. Allow one deliberate retry of the rejected attempt with a retained audit record.
6. Move the default branch while another PR is ready. Show the blocker, synchronize through the configured repair path, rerun trusted checks and merge only the eligible revision.
7. Lose GitHub access, close the desktop, kill the dashboard process and restart the daemon. Preserve queue state, show data freshness and restore visibility without starting a second dispatcher.
8. Create a future phase with a genuine customer or spending dependency. Start independent synthetic development automatically and make the specific missing external fact visible. Avoid a generic hidden approval stop.
